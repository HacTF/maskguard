# 浏览器插件统一纳管可行性验证报告

> 验证对象：**一个服务端能否监控浏览器插件的安装状态，并对插件统一下发策略**
> 验证方式：读业界方案 + 自建可运行 PoC（服务端 + 真实 MV3 插件 + 真实 Chromium）跑通全链路
> 结论日期：2026-11-15

---

## 一、结论

| 能力 | 可行性 | 说明 |
|---|---|---|
| 服务端查看插件是否**已安装并启用** | ✅ 可行 | 插件注册 + 心跳上报，PoC 已实测 |
| 服务端查看插件**版本 / 策略版本 / 应用失败原因** | ✅ 可行 | ACK 回执带回成功或错误原因，PoC 已实测 |
| 服务端**统一下发策略**并保证最终一致 | ✅ 可行 | 版本化策略 + 拉取 + 幂等应用 + ACK，PoC 已实测（含回滚） |
| 服务端主动发现**没装 / 被卸载 / 被禁用**的终端 | ⚠️ **纯插件做不到** | 没装就不会说话。只能靠「资产台账差集」或「企业策略强制安装 + 合规报表」 |
| 阻止用户卸载插件 | ⚠️ 无「卸载密码」这种东西 | 但企业策略 `force_installed` 等效：用户看不到卸载/停用开关 |
| 万级终端规模 | ✅ 可行 | 5000 插件实测：心跳 4019 req/s，p95 29ms，内存 +63MB |

**一句话**：控制面（状态可见 + 策略可下发）技术成熟、成本低；真正的难点不在技术，而在**覆盖率的保证方式**——必须借企业策略把插件"钉"在浏览器里，否则服务端永远有盲区。

---

## 二、为什么"安装状态"必须拆成两件事

```
已安装且启用  ──心跳──▶ 服务端看得见（100% 可信）
未安装/被卸载 ──没有心跳──▶ 服务端只能推断（不可信）
```

所以"监控安装状态"实际是两套机制的组合：

| 机制 | 覆盖对象 | 数据来源 | 可信度 |
|---|---|---|---|
| 心跳纳管 | 装了且启用的 | 插件主动上报 | 高（有签名，防伪造） |
| 资产对账 | 应装未装的 | 域控/Intune/CMDB 台账 − 已注册清单 | 中（取决于台账准不准） |
| 强制安装 | 全部受管终端 | 企业策略 `ExtensionInstallForcelist` | 高（策略级强制） |

**只有三者叠加，"哪些机器没装"才是可回答的问题。**

## 三、防卸载：没有密码，但有等效手段

| 手段 | 效果 | 前提 |
|---|---|---|
| 扩展自身 API | **做不到**，无任何接口能拦截卸载 | — |
| `ExtensionInstallForcelist` | 用户无移除/停用开关，界面显示"由你的组织管理" | 写 HKLM 注册表或 GPO/Intune 下发 |
| `ExtensionSettings` | 同上，且可禁装其它扩展、限制权限 | 同上，粒度更细 |
| Chrome/Edge 云管理 | 远程下发，不必加域 | 浏览器登录企业账号/受管 |
| 主机侧巡检（脚本/EDR） | 不阻止，但能**发现**被卸载并告警 | 需要另一个常驻代理 |

**边界**：拦不住换便携版浏览器、删配置目录、重装系统。所以定位应是"提高门槛 + 可检测"，不是"绝对防卸载"。

**可观测替代方案**：插件用 `chrome.management.getSelf()` 上报 `installType`（`admin`=策略强制安装 / `normal`=商店安装 / `development`=开发者加载）与 `mayDisable`。服务端据此把每台标成「托管 / 可被用户卸载」——即使没有卸载密码，也能把风险变成指标。PoC 已实现并验证（本次为 `development`，`mayDisable=true`，属于预期）。

### 4.3 实测暴露的真实约束

| 约束 | 表现 | 应对 |
|---|---|---|
| MV3 Service Worker 会被回收 | 心跳不能依赖常驻定时器 | 用 `chrome.alarms`（最小 30s）+ 页面事件触发即时同步 |
| 策略不是"秒达" | 依赖下一次同步时机 | 页面加载/切换时主动 pull，安全网是 30s 心跳；要秒级需长连接（SSE/WebSocket），但 SW 生命周期会把连接掐断 |
| 插件拿不到主机名 | 浏览器沙箱不暴露 OS hostname | 主机标识需由企业策略/安装包注入（`config.json` 或 managed storage） |
| `--load-extension` 只能是 development | 无法在测试环境复现 `admin` 强制安装态 | 生产用 GPO/Intune 下发后，`installType` 才会变 `admin` |

## 五、三种落地路线

| 路线 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. 自建控制台**（本 PoC） | 插件拉取策略，服务端存版本与回执 | 完全自主、可审计、可灰度、与业务规则强耦合 | 需自己保证覆盖率；要处理服务端不可达的兜底 | 已有企业分发能力、策略需频繁调整 |
| **B. 纯企业策略** | 把规则直接写进 `chrome.storage.managed`，GPO/Intune 下发 | 无需自建服务端、强制安装、改策略即时生效 | 每次改规则要重新下发策略；无运行态数据（不知道谁在用、命中多少） | 策略极少变、只要"钉住" |
| **C. A+B 组合**（推荐） | managed 只放「服务端地址 + 注册令牌 + 主机标识」，业务规则走服务端拉取 | 既是强制安装（防卸载），又有运行态与灰度能力 | 两套机制都要维护 | 生产环境 |

推荐 C：`managed` 负责"装得上、卸不掉、知道连哪个服务端"，服务端负责"策略内容 + 运行态 + 对账"。

## 六、生产化差距（PoC 未做，但必须做）

| 项 | PoC 现状 | 生产要求 |
|---|---|---|
| 传输安全 | HTTP | HTTPS，建议 mTLS 或证书固定 |
| 插件鉴权 | 注册令牌 + 每插件 HMAC 密钥 | 密钥定期轮换；令牌按部门/批次签发，泄露可吊销 |
| 存储 | 单 JSON 文件 | PostgreSQL（终端表 + 策略版本表 + 审计表） |
| 策略灰度 | 全量下发 | 按部门/批次/百分比灰度，异常自动停止 |
| 审计 | 事件流（内存 + 文件） | 落库 + 保留期 + 导出，满足等保审计要求 |
| 高可用 | 单进程 | 多实例 + 共享存储；心跳路径无状态化 |
| 插件更新 | 手动 | 自建 CRX 更新服务（`update_url`）+ 版本强制下限 |
| 观测 | 无 | 心跳成功率、收敛时延、失败原因分布看板 |

## 十、结论复述

1. **能做**：状态纳管、策略下发、回执、回滚、对账，全链路已在真实浏览器上跑通，成本约 30 人天。
2. **做不到**：服务端无法凭空知道"谁没装"；也没有"卸载密码"，只能用企业策略强制安装 + 台账对账逼近。
3. **建议**：managed 策略管"装得上、卸不掉"，服务端管"策略内容 + 运行态"，两条腿走路。
